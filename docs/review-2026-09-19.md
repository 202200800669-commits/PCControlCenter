## 必须优先修复

### P1-1：“恢复自动”实际请求最低转速试运行

位置：`src/PCControlCenter.Desktop/Views/CoolingView.cs:36`；`ViewModels/MainViewModel.cs:581` 附近。

按钮调用 RunFanTrialAsync(1500,1500,5)，后者固定创建 manual 请求。实际行为是先把双风扇目标降到 1500 RPM，维持 5 秒后再走试运行恢复，并非立即恢复自动。若 IsBusy 为 true，还会直接返回，无法停止当前试运行。

修复：独立实现 auto 请求和停止当前试运行的明确生命周期；取消当前会话后等待恢复回执，不能借低速试运行实现恢复。增加按钮到请求类型的测试，并检查忙碌时停止行为。

### P1-2：桌面端将业务失败显示为成功

位置：`src/PCControlCenter.Desktop/ViewModels/MainViewModel.cs:480`、`:515`、`:593`。

模式和能源设置只判断外层 resp.Code == OK 和回执存在，随后将目标值直接写入 UI，并记录成功。Broker 即使收到 CONTROL_FAILED、TARGET_NOT_REACHED 或 ROLLBACK_FAILED 回执，也会在外层返回 OK，因为这只表示代理完成了请求处理。风扇路径同样不检查实际 Code，直接显示试运行完成。

修复：分别判断传输状态、业务 Code、FinalMode/FinalValue 读回与 Recovery；成功时只显示确认的实际值。失败或恢复未确认应保留明确状态，不能被后续刷新统一“已连接”覆盖。以本次故障回执作为桌面回归测试输入。

### P1-3：写入异常绕过恢复，超时又直接杀死工作进程

位置：`src/PCControlCenter.Providers.Windows/ModeSession.ps1:66`、`:101`；`EnergySession.ps1:122`、`:157`；两个 SessionRunner 的 `:47`。

回滚仅位于“轮询完成但未确认目标”的分支。首次设置已部分成功后抛异常、或后续读回抛异常，会直接进入外层 catch，返回 CONTROL_FAILED / NOT_NEEDED，不回滚。充电设置本身由多条 DeviceIoControl 组成，这种部分写入场景需要单独处理。本次模拟确认两个工作进程均出现该问题。

另外，Mode/Energy Runner 在超时或取消时直接 Kill 工作进程，无法保证恢复代码执行。Get-ItsMode 也未拒绝无法恢复的旧模式（例如 4），缺失值转换为 int 还可能被视作 0。

修复：写前验证旧状态可恢复；在开始写入前设置 touched 标记，所有异常路径都尝试恢复，并明确区分恢复成功与未知结果。使用协作停止机制，不能在正在恢复时直接终止工作进程。补充第二条充电命令失败、读回异常、恢复异常、旧模式 4/缺失值与超时取消测试。

### P1-4：模式/能源与风扇会话的互斥检查存在空档

位置：`src/PCControlCenter.Providers.Windows/ModeSession.ps1:49`；`EnergySession.ps1:105`。

两个工作进程都先获取风扇锁，立即释放，然后才获取各自功能锁并执行设置。风扇工作进程只持有风扇锁，因此可以在模式切换中途启动。现有测试只验证“风扇先持锁”，未覆盖相反顺序。本次在模式写入时启动独立锁探测进程，结果为 True，确认空档。

修复：整个设置、读回和恢复期间持有共同的硬件控制锁；统一获取顺序，避免死锁。补充两个启动顺序的跨进程竞争测试。

## 仍需完成的功能与可靠性工作

### P2-1：设备识别失败时伪造参考机身份，桌面读取绕过适配器选择

位置：`ViewModels/MainViewModel.cs:387`、`:450`；`Services/EnergyReader.cs:21`。

识别失败后直接生成 ThinkBook 21R0/R2CN57WW 身份。遥测又对所有设备调用 Lenovo EnergyDrv 原生读取，没有先通过精确设备匹配。GPU 文本还写死为 NVIDIA 5060（`:432`）。这使未知设备的显示、诊断和探测路径失真。

Broker 仍重新识别真实机器，因此本次未发现伪造桌面身份直接绕过 Broker 写入白名单；不要将该问题误写为“任意品牌已能写入”。应在识别失败时保持未知状态并关闭专用控制，把专用读取归回适配器，型号文字来自真实数据。

### P2-2：亮度、场景应用和设置持久化未接通

- `Views/DeviceView.cs:31`：亮度滑块只更新文字，没有实际设置调用，也没有绑定真实初始亮度。
- `Views/ProfilesView.cs:51`：应用场景只切换性能模式，不应用 Brightness 或 FanKind。名为“全速散热”的预设不会因此启动全速。
- `Views/ProfilesView.cs:74`：保存只修改内存集合，却提示已保存；桌面工程没有接入 PreferenceStore 或其他配置持久化，重启后修改丢失。
- `Views/CoolingView.cs:49` 起：风扇滑块只更新目标显示，仍需按钮启动；LatestControlQueue 未接入桌面。这与“拖动即应用”的需求尚有距离。

这些属于业务实现，不能靠换 Figma 样式解决。应实现后再启用相关入口，或明确标为暂未支持。

### P2-3：刷新间隔设置无效，异步轮询可能重叠

位置：`MainWindow.cs:64`；`Views/SettingsView.cs:80`。

timer.Interval 只在构造时读取一次，设置页只修改 VM 属性，之后并未更新计时器。Tick 是 async 事件处理且没有串行防护，慢探针尚未结束时下一次 Tick 或手动刷新可以再次进入。

修复：连接间隔变更，并采用单一可取消的串行监控循环；重启监控时等待前一轮退出。

### P2-4：诊断快照长期不刷新，失效数据仍被当成连接正常

位置：`ViewModels/MainViewModel.cs:394`、`:400` 起；`Views/SettingsView.cs:106` 起。

CurrentSnapshot 仅初始化时赋值，之后刷新遥测、切换模式、提权读取都不更新该快照，导出会使用启动时的旧数据。GPU、模式、能源读取失败时，部分字段不清空，最后仍统一写“已连接”。长时间运行后可能展示失效旧值，导出与屏幕也不一致。

修复：统一采样快照、时间与可用性，失败时明确失效；导出前刷新或明确标记采样时间，不能用导出时间代替采样时间。
