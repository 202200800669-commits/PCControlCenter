## P1：Process 所有权没有真正移交给后台跟踪器

位置：`src/PCControlCenter.Providers.Windows/ModeSessionRunner.cs:41、65`、`EnergySessionRunner.cs:41、65`；`RecoveryProcessTracker.cs:23-61`。

Runner 通过 using var 持有 Process。超时调用 Track(process) 后返回，using 随即 Dispose 同一个对象。后台任务可能因此异常退出并移除记录，HasInFlightRecovery 也可能访问已释放对象。原进程没有因 Dispose 自动结束。

补充实验使用只执行 Start-Sleep 的自有子进程，按生产顺序 Track 后 Dispose，得到：

```text
TrackerAfterCallerDispose=False
ChildStillAlive=True
```

实验结束已清理该自有子进程。没有触碰硬件或生产控制进程。

修复：定义唯一生命周期所有者。移交后调用方不得再释放 Process、输出流等仍由后台读取的资源；后台只在工作者退出并处理最终回执后清理。获取 HasInFlightRecovery 时应能正确处理异常进程状态。测试必须覆盖“Runner 返回之后”，不能只覆盖 Track 后立即查询。

## P1：恢复跟踪仅存在于即将退出的 Broker 进程中

位置：`RecoveryProcessTracker.cs:9-23`；`src/PCControlCenter.Broker/Program.cs` 返回响应并退出的路径。

跟踪器是进程内 static 列表和 Task.Run。当前 Broker 是一次性进程，返回超时回执后 Main 结束；后台线程池任务不会让进程继续存活。下一次请求启动新的 Broker，不共享这个列表。mutexNames 参数也没有使用，无法把它解释为跨进程恢复登记。

现有工作者仍持有自身硬件 mutex，这可继续拦截一部分并发写入，但不是新的后台跟踪、最终回执和资源清理已经成立的证明。另外，Tracker 仍在十分钟后 Kill(true)，只是把旧的强杀迁移到了另一层。

修复：先明确架构边界，再实现其一：让 Broker 在恢复结束、收集回执前保持受管理的存活状态，或建立独立、持续存在的恢复管理进程。必须处理客户端断开后的结果记录、输出流、工作者自然退出及异常退出。新请求通过可信的跨进程状态/互斥约束判断是否允许控制。不要继续叠加进程内字典或延长 Kill 时间充当解决方案。

验收：独立进程集成测试，前端/请求返回后恢复仍被可靠管理；第二个 Broker 进程看到一致约束；恢复结束后记录最终结果并清理。测试工作者全部使用假硬件。

## P2：会话状态表没有接到原工作者最终回执

位置：`src/PCControlCenter.Desktop/Services/BrokerExecutor.cs:97-107、126-183`；`MainViewModel.cs:1031`。

BrokerSessionTracker 只由桌面侧更新。取消后 ExecuteAsync 标记 Recovering 并抛出，原通信已结束，没有后台通道把工作者最终回执写回表内。WaitForRecoveryAsync 仍根据全局 mutex 推测状态：取得锁即把 Running / Recovering 转为 RecoveryCompleted，甚至用 NOT_NEEDED 补空恢复值；锁不存在则推测异常终止。锁可用不能区分正常恢复与恢复失败，缺锁也不能证明工作者已经退出。

此外，ExecuteAsync 收到任意 Broker 响应就记 RecoveryCompleted，包括错误或 UNCONFIRMED；视图模型最终仍无条件 IsBusy=false。当前不会把所有分支都显示为“已恢复自动”，但状态模型仍混淆通信结束、互斥释放与恢复终态。

修复：使用真实请求 ID 对应的工作者状态和最终回执更新记录，区分通信完成、工作者结束、恢复成功与未确认。mutex 只用于互斥，不能补造恢复结果。未确认状态保留可操作的后续核查/恢复路径及适当控制限制，避免无条件回到普通空闲。

验收：真实跨进程 mock 测试覆盖锁尚未创建、正常恢复、恢复失败但锁已释放、进程崩溃、超时后迟到回执。不能仅由 fake 返回枚举值证明真实协议已实现。

## P1（测试隔离）：默认测试再次依赖计时来阻止真实硬件调用

位置：`tests/PCControlCenter.Tests/DesktopViewModelTests.cs:419-434`。

测试启动 `ping ... -n 3`，再调用真实的 ModeSessionRunner / EnergySessionRunner，期望跟踪器返回 BUSY。若辅助进程在调用前退出，HasInFlightRecovery 会移除记录，接下来可能进入真实硬件逻辑。测试机器恰好匹配受支持型号时尤其不能依赖此条件。

修复：注入工作者启动器或不可调用真实硬件的执行器，测试中只要越过预期 BUSY 分支就直接失败。辅助进程采用显式握手与释放，不依赖两秒存活窗口。断言本身不能替代隔离。

验收：故意在检查与调用之间延迟超过三秒，或者让模拟跟踪器失效，测试只能安全失败，不能启动生产硬件脚本。完成后再运行完整 verify。
